## 1. 方案概述

### 1.1 设计目标

将 Metrics Mall 从单租户架构升级为多租户 SaaS 平台，实现：

- **多租户隔离**: 数据、资源、配置完全隔离
- **弹性扩展**: 按需分配资源，支持从免费版到企业版
- **统一管理**: 统一的管理后台，简化运维
- **成本优化**: 资源共享，降低单租户成本
- **快速接入**: 5 分钟注册，即开即用

### 1.2 核心原则

1. **数据安全优先**: 租户数据物理或逻辑隔离，互不可见
2. **资源公平分配**: 配额管理，防止单租户占用过多资源
3. **性能隔离**: 单租户异常不影响其他租户
4. **成本可控**: 按使用量计费，透明定价

## 2. 多租户架构设计

### 2.1 租户模型

```
┌─────────────────────────────────────────┐
│           SaaS Platform                 │
│                                         │
│  ┌──────────┐  ┌──────────┐            │
│  │ Tenant A │  │ Tenant B │            │
│  │ (Free)   │  │ (Pro)    │            │
│  └──────────┘  └──────────┘            │
│                                         │
│  ┌──────────┐  ┌──────────┐            │
│  │ Tenant C │  │ Tenant D │            │
│  │ (Pro)    │  │ (Enterprise)│          │
│  └──────────┘  └──────────┘            │
│                                         │
└─────────────────────────────────────────┘
```

**租户标识 (Tenant ID)**:
- 格式: `t_{uuid}` 或 `t_{org_id}`
- 全局唯一，不可修改
- 所有数据、资源、配置都关联 Tenant ID

### 2.2 数据隔离方案

#### 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **共享数据库，共享表** | 成本最低，运维简单 | 数据安全风险高，性能隔离难 | 不推荐 |
| **共享数据库，独立表** | 成本适中，数据隔离好 | 表数量多，管理复杂 | 中小规模 |
| **独立数据库** | 数据完全隔离，性能好 | 成本高，资源浪费 | 企业版 |
| **混合方案** | 灵活，按需分配 | 实现复杂 | **推荐** |

#### 推荐方案：混合隔离

```
┌─────────────────────────────────────────┐
│          SaaS Platform                  │
│                                         │
│  ┌──────────────────────────────┐      │
│  │  共享数据库 (Shared DB)        │      │
│  │  - 免费版/标准版租户            │      │
│  │  - 表名: {tenant_id}_metric    │      │
│  └──────────────────────────────┘      │
│                                         │
│  ┌──────────────────────────────┐      │
│  │  独立数据库 (Dedicated DB)      │      │
│  │  - 企业版租户                  │      │
│  │  - 完全隔离                    │      │
│  └──────────────────────────────┘      │
│                                         │
└─────────────────────────────────────────┘
```

**实现细节**:

1. **MySQL (元数据)**:
   - 共享数据库: `metrics_mall_shared`
   - 表命名: `{tenant_id}_metric`, `{tenant_id}_dim`, `{tenant_id}_entity_meta`
   - 独立数据库: `metrics_mall_{tenant_id}` (企业版)

2. **Redis (热存储)**:
   - Key 前缀: `{tenant_id}:mx:{metric_code}:{dim_suffix}:v{version}`
   - 示例: `t_abc123:metric:coin_balance:user_12345`
   - 可选: 企业版使用独立 Redis 实例

3. **ClickHouse (冷存储)**:
   - 表命名: `metrics_{tenant_id}`
   - 分区键包含 `tenant_id`
   - 查询自动过滤 `tenant_id`

4. **Kafka (消息队列)**:
   - Topic 命名: `metrics.raw.{tenant_id}`
   - 分区策略: 按 `tenant_id` 哈希分区

### 2.3 资源隔离方案

#### Redis 资源隔离

```yaml
# 共享 Redis Cluster
Redis Key 格式: {tenant_id}:{namespace}:{key}
示例: t_abc123:metric:coin_balance:user_12345

# 配额管理
- 每个租户分配独立的内存配额
- 使用 Redis Hash 存储租户配额信息
- 超限时触发 LRU 淘汰（仅淘汰该租户的 Key）
```

#### ClickHouse 资源隔离

```sql
-- 表结构包含 tenant_id
CREATE TABLE metrics_t_abc123 (
    tenant_id String,
    metric_name String,
    timestamp UInt64,
    dims Map(String, String),
    value Float64
) ENGINE = MergeTree()
PARTITION BY (tenant_id, toYYYYMM(toDateTime(timestamp)))
ORDER BY (tenant_id, metric_name, timestamp);

-- 查询自动过滤
SELECT * FROM metrics_t_abc123 
WHERE tenant_id = 't_abc123' 
  AND metric_name = 'coin_balance';
```

#### Flink 资源隔离

```yaml
# 按租户分配 Flink TaskManager
- 共享模式: 所有租户共享 Flink 集群，通过租户 ID 路由
- 隔离模式: 企业版租户分配独立的 Flink TaskManager

# 配额限制
- 每个租户的并发任务数限制
- 每个租户的 CPU/内存配额
- 流控: 单租户数据量超限时降级处理
```

### 4.3 配额检查与限流

**实时配额检查**:

```java
// 伪代码
public class QuotaChecker {
    public boolean checkEventQuota(String tenantId, int eventCount) {
        TenantQuota quota = getTenantQuota(tenantId);
        TenantUsage usage = getCurrentUsage(tenantId);
        
        if (usage.getEventCountThisMonth() + eventCount > quota.getEventLimitMonthly()) {
            return false;  // 超限
        }
        return true;
    }
    
    public void enforceRateLimit(String tenantId, String apiType) {
        // Redis 计数器限流
        String key = String.format("rate_limit:%s:%s", tenantId, apiType);
        long count = redis.incr(key);
        redis.expire(key, 1);  // 1秒过期
        
        int limit = getQuotaLimit(tenantId, apiType);
        if (count > limit) {
            throw new RateLimitExceededException();
        }
    }
}
```

**超限处理策略**:

1. **事件量超限**: 
   - 拒绝写入，返回 429 Too Many Requests
   - 发送告警通知
   - 提供升级引导

2. **QPS 超限**:
   - 限流（令牌桶算法）
   - 返回 429，提示重试时间

3. **存储超限**:
   - 自动清理最旧数据
   - 发送告警通知
   - 提供扩容选项

## 7. API 网关设计

### 7.1 网关职责

1. **认证拦截**: 验证 API Key，提取 Tenant ID
2. **租户上下文**: 注入 Tenant Context 到请求头
3. **限流控制**: 基于租户配额限流
4. **路由转发**: 转发到后端服务
5. **监控统计**: 记录请求日志、使用量

### 7.2 实现方案

**方案 1: Spring Cloud Gateway** (推荐)

```java
@Configuration
public class GatewayConfig {
    
    @Bean
    public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {
        return builder.routes()
            .route("metrics-api", r -> r
                .path("/api/**")
                .filters(f -> f
                    .filter(tenantAuthFilter())
                    .filter(rateLimitFilter())
                )
                .uri("lb://metrics-mall-service"))
            .build();
    }
    
    @Bean
    public GatewayFilter tenantAuthFilter() {
        return (exchange, chain) -> {
            ServerHttpRequest request = exchange.getRequest();
            String apiKey = extractApiKey(request);
            
            // 验证 API Key，获取 Tenant ID
            TenantContext tenant = authService.validateApiKey(apiKey);
            
            // 注入 Tenant Context
            ServerHttpRequest modifiedRequest = request.mutate()
                .header("X-Tenant-Id", tenant.getTenantId())
                .header("X-User-Id", tenant.getUserId())
                .build();
            
            return chain.filter(exchange.mutate().request(modifiedRequest).build());
        };
    }
}
```

**方案 2: Kong / Nginx + Lua**

```lua
-- kong/plugins/tenant-auth.lua
local TenantAuth = {
    PRIORITY = 1000,
    VERSION = "1.0.0"
}

function TenantAuth:access(conf)
    local api_key = kong.request.get_header("X-API-Key")
    if not api_key then
        return kong.response.exit(401, {message = "Missing API Key"})
    end
    
    -- 验证 API Key
    local tenant = validate_api_key(api_key)
    if not tenant then
        return kong.response.exit(401, {message = "Invalid API Key"})
    end
    
    -- 注入 Tenant Context
    kong.service.request.set_header("X-Tenant-Id", tenant.tenant_id)
    kong.service.request.set_header("X-User-Id", tenant.user_id)
    
    -- 限流检查
    local ok, err = rate_limit_check(tenant.tenant_id)
    if not ok then
        return kong.response.exit(429, {message = "Rate limit exceeded"})
    end
end

return TenantAuth
```

## 9. 数据迁移方案

### 9.1 从单租户迁移到 SaaS

**迁移步骤**:

1. **数据导出**:
   ```bash
   # 导出 MySQL 数据
   mysqldump -u root -p metrics_mall > metrics_mall_backup.sql
   
   # 导出 ClickHouse 数据
   clickhouse-client --query "SELECT * FROM metrics" > metrics_backup.csv
   ```

2. **数据转换**:
   - 为所有表添加 `tenant_id` 字段
   - 更新所有数据，设置 `tenant_id = 't_migrated_xxx'`
   - 更新 Redis Key，添加 `tenant_id` 前缀

3. **数据导入**:
   - 导入到 SaaS 平台的共享数据库
   - 验证数据完整性

### 9.2 租户数据导出

**支持租户导出自己的数据**:

```sql

SELECT * FROM t_abc123_metric;

SELECT * FROM tenant_usage WHERE tenant_id = 't_abc123';

-- 导出 ClickHouse 数据（需要按租户过滤）
SELECT * FROM metrics_t_abc123 
WHERE timestamp >= UNIX_TIMESTAMP('2024-01-01') * 1000;
```
