# 需求方评审意见：双速实时指标系统

**评审日期**: 2025-01-15  
**评审角色**: 需求方/产品评审者  
**文档版本**: v1.0

---

## 一、总体评价

### 优点

#### 1. 产品定位清晰
- **双速架构设计**（GMS/GMA）能同时满足实时决策和历史分析需求，架构思路清晰
- **目标用户明确**（中小企业广告投放团队、独立开发者），避免了"大而全"的陷阱
- **核心价值主张**（高性价比、即插即用）符合目标用户痛点

#### 2. 技术选型合理
- **Redis + ClickHouse** 的读写分离设计符合场景需求
- **Flink 双路分发**保证数据一致性，技术方案成熟
- **Lambda 架构变体**在实时性和成本之间取得平衡

#### 3. 商业场景具体
- **广告投放效果聚合看板**场景描述清晰，痛点明确（数据分散、人工整合、无法实时监控）
- **定价策略**有初步思考（¥299/月起），但需要更多成本支撑

## 二、需要改进的地方

### 1. 产品定位与目标用户匹配度 ✅ 部分解决

**问题**：
- 目标用户是"中小企业广告投放团队"，但技术栈复杂度较高（Kafka + Flink + ClickHouse）
- 中小企业通常缺乏运维能力，自建部署门槛过高
- 文档中提到的"单机或小集群"与实际的组件数量（Kafka 3节点、Redis Cluster 3主3从）存在矛盾

**已解决**：
- ✅ **已提供 Docker Compose 一键部署方案**（见 `docs/design/DOCKER-DEPLOYMENT.md`）
  - 简化版：单节点部署，适合中小企业快速启动
  - 生产版：集群模式，支持高可用扩展
  - 一键启动脚本：`scripts/quick-start.sh`
  - 完整文档：包含部署、配置、维护、故障排查指南

**仍需完善**：
- 明确"中小企业"的定义（团队规模、技术能力、预算范围）
-✅ **已提供托管 SaaS 模式**，降低使用门槛
- 区分"自建版"和"SaaS版"两种产品形态

### 2. API 设计易用性 ⚠️ 中优先级

**问题**：
- ~~GMS 接口路径较长：`/api/m/{entity_code}/{entity_id}/{metric_codes}`，不够 RESTful~~ ✅ 已改进
- ~~GMS 接口无法为不同metric指定不同的维度条件~~ ✅ 已改进（改为POST，支持每个metric独立配置dims）
- GMA 使用 POST，但语义更像查询操作

**建议**：

    {"code": "risk_score", "dims": {"os": "ios"}}
  ]
}

// GMA 考虑支持 GET（简单查询）+ POST（复杂查询）

GET /api/v1/m_agg?metric=pay_amount&start=...&end=...  // 简单查询**改进点**：
-✅ 增加 API 版本号（`/api/v1/`）
-✅ GMS 接口改为 POST，支持每个metric独立配置维度条件
- 提供 OpenAPI/Swagger 文档
- 增加 SDK 示例代码（Java/Python/Go）

### 3. 错误处理与用户体验 ⚠️ 中优先级

**问题**：
- 错误码设计偏技术化（40001, 40002），用户理解成本高
- 缺少常见错误场景的处理建议
- 没有错误码到用户语言的映射

**建议**：
- 增加业务友好的错误提示
- 提供错误码对照表（技术错误码 → 用户友好提示）
- 增加常见错误场景的处理建议
- 考虑支持多语言错误消息

**示例**：
{
"code": 40001,
"errmsg": "指标不存在",
"user_message": "您查询的指标 'coin_balance' 不存在，请检查指标名称或联系管理员",
"suggestion": "查看可用指标列表: GET /api/v1/m/{metric_code}/versions/{version}/list"
}---

### 4. 数据安全与权限 ⚠️ 高优先级

**问题**：
- 文档中**完全没有**提到权限控制、多租户、数据隔离
- 缺少 API Key 认证机制
- 没有数据隐私和合规说明（GDPR、数据加密）

**建议**：
- **多租户隔离方案**：
    - 数据隔离：每个租户的数据物理隔离或逻辑隔离
    - 资源隔离：Redis/ClickHouse 按租户分配资源
- **权限控制**：
    - API Key 认证机制
    - 角色权限（只读、读写、管理员）
    - 指标级别的权限控制
- **数据安全**：
    - 数据传输加密（HTTPS）
    - 数据存储加密（可选）
    - 数据访问审计日志
- **合规性**：
    - GDPR 合规说明
    - 数据保留策略
    - 数据删除机制

### 5. 成本与定价 ⚠️ 高优先级

**问题**：
- 定价（¥299/月起）缺少成本支撑
- 没有说明超出配额的处理方式
- 缺少资源消耗模型

**建议**：
- **资源消耗模型**：
    - 明确 100 万事件/天的服务器成本
    - 提供成本计算器（事件量 → 资源消耗 → 成本）
- **配额管理**：
    - 明确免费额度（10万事件/月）
    - 超出配额的处理（限流/降级/额外收费）
    - 提供配额使用情况查询接口
- **定价策略**：
    - 按事件量阶梯定价
    - 按存储时长定价
    - 按查询 QPS 定价
    - 提供成本优化建议

### 6. 监控与运维 ⚠️ 中优先级

**问题**：
- 文档提到"监控告警配置（Prometheus+Grafana）"，但这是**运维视角**
- 缺少**用户视角**的监控能力（系统健康、数据延迟）

**建议**：
- **用户监控看板**：
    - 系统健康状态（Redis/ClickHouse 可用性）
    - 数据延迟监控（端到端延迟、各组件延迟）
    - 配额使用情况
- **告警能力**：
    - 支持自定义告警规则（如指标异常阈值）
    - 告警通知（邮件、短信、Webhook）
    - 告警历史记录
- **SLA 承诺**：
    - 明确 SLA 指标（可用性 99.9%、延迟 <10ms）
    - 提供 SLA 补偿机制（如服务中断补偿）

## 四、关键问题清单

在进入 MVP 开发前，建议明确以下问题：

### 产品定位
- [ ] 目标用户的技术能力范围是什么？
- [ ] 提供自建版还是 SaaS 版，还是两者都提供？
- [ ] 如果提供 SaaS 版，服务器部署在哪里（国内/海外）？

### 技术架构
- [ ] 多租户隔离方案（物理隔离 vs 逻辑隔离）？
- [ ] API 认证机制（API Key vs OAuth2）？
- [ ] 数据加密策略（传输加密、存储加密）？

### 商业模型
- [ ] 定价模型（按事件量、按存储、按查询 QPS）？
- [ ] 免费额度是多少？
- [ ] 超出配额的处理方式（限流/降级/额外收费）？

### 用户体验
- [ ] SDK 支持哪些语言（Java/Python/Go/其他）？
- [ ] 是否有管理后台（指标配置、数据查询、监控告警）？
- [ ] 是否有技术支持（文档、FAQ、工单系统）？

4. **明确商业价值**：完善成本模型、定价策略、ROI 分析

建议在进入 MVP 开发前，**优先解决高优先级问题**，确保产品既技术可行，又商业可行。
