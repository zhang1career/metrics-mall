---

## 一、 总体评估与核心痛点

### 1.1 核心优势 (Keep)
* ✅ **双速架构 (Dual-Speed)**：GMS（毫秒级实时）与 GMA（秒级OLAP）分离设计合理，兼顾了交易侧的高并发与分析侧的灵活性。
* ✅ **技术栈稳健**：Kafka + Flink + Redis + ClickHouse 是业界成熟方案，无明显技术风险。
* ✅ **多租户 SaaS 能力**：隔离方案与配额管理清晰，适合规模化扩展。

### 1.2 核心痛点 (Fix)
* ❌ **“黑盒”恐惧**：用户不知道指标计算对不对（缺乏调试），不知道依赖关系（缺乏血缘），不知道数据准不准（缺乏质量监控）。
* ❌ **场景深度不足**：交易场景缺事务性，信贷场景缺解释性，推荐场景缺向量支持。
* ❌ **流程不确定性**：缺乏明确的数据修正、维度热加载及安全的上下线流程。

## 二、 核心功能增强：消除“黑盒” (Core Platform Features)

针对所有用户最基础的诉求，必须建立信任感。

### 2.1 指标调试与全景图 (Debugger & Catalog)
**痛点**：定义了 `gmv = amount * rate`，点完提交心里没底，上线即故障；新人不知道 `user_status` 到底依赖谁。

* **功能 1：在线试算/调试器 (Metric Debugger)**
    * **UI 交互**：提供“试运行”按钮。用户输入一条模拟 JSON 日志，界面直接展示 Flink 解析后的 Key 和 Value。
    * **API 支持**：提供 `simulate` 接口，支持输入假设条件（如“假设还款1000元”）查看指标变化（信贷场景刚需）。
* **功能 2：指标全景字典 (Data Catalog)**
    * **电商化搜索**：支持搜“日活”、“风险分”。
    * **血缘可视化**：展示 `ODS表 -> Flink任务 -> Redis Key` 的全链路。
    * **应用热度**：显示指标被哪些 API 调用、QPS 多少，辅助下线决策。

### 2.2 API Playground (在线调试台)
**痛点**：开发人员接入成本高，Redis 和 CK 数据存在延迟差，容易误判系统故障。

* **形态定义**：后台嵌入 Swagger 或 Postman 风格页面，必须聚合 **GMS (实时)** 和 **GMA (历史)** 两种模式。
* **界面逻辑**：
    * **选择模式**：`[ (o) 实时决策接口 (A) ]` vs `[ ( ) 历史分析接口 (B) ]`
    * **环境/实体**：输入 `User` + `u123456`
    * **响应展示**：直接透传 Redis/CK 结果，并附带 `debug_info` (如数据来源节点、延迟)。

### 2.3 智能监控与健康灯 (Observability)
**痛点**：运营不知道指标跌零，用户发现 Redis 与 CK 数据不一致。

* **功能 1：指标“健康灯” (Health Lights)**
    * 在列表页显示绿/红灯。逻辑：过去 10 分钟 Flink 无产出即亮红灯。让运营一眼看到状态。
* **功能 2：用户级告警配置**
    * **实时阈值**：`metrics:gmv < 1000` 持续 1 分钟 -> 钉钉/Webhook 通知。
    * **趋势异动**：今日 GMV 同比昨日下跌 50% -> 报警。
* **功能 3：数据一致性探针**
    * 提供 API 检查 Redis 与 ClickHouse 的数据一致性与延迟差（`consistency_check`）。

## 三、 业务场景深度优化 (Domain-Specific Features)

针对不同业务线的垂直需求进行增强。

### 3.1 交易场景：一致性与版本
* **事务性快照查询**：
    * **需求**：保证查询余额和冻结金额时，是同一时刻的快照。
    * **方案**：API 增加 `snapshot_ts` 或 `atomic: true` 参数。
* **指标版本管理**：
    * **需求**：风控算法升级，需同时支持 v1 和 v2 版本并行跑。
    * **方案**：Redis 保留多版本，API 支持 `POST /api/v1/m_snap { "version": 2 }`。

### 3.2 信贷场景：解释性与规则
* **指标解释性 (Explainability)**：
    * **需求**：不仅要返回风险分 0.85，还要解释“因为逾期3次，权重0.3”。
    * **方案**：API 响应增加 `explanations` 字段，通过元数据返回计算公式与因子。
* **指标置信度**：
    * **需求**：数据源如果更新不及时，需要告知业务方。
    * **方案**：返回 `confidence` 字段（数据质量分、最后更新时间）。

### 3.3 推荐场景：向量与实时特征
* **向量指标支持**：
    * **需求**：用户 Embedding 特征存储与查询。
    * **方案**：支持 `value_type: vector`，并提供相似度计算接口。
* **特征增量更新**：
    * **需求**：点击行为实时改变兴趣标签权重。
    * **方案**：支持 `increment` 操作原子更新特征值。

## 四、 关键工作流程闭环 (Critical Workflows)

流程的不确定性是系统烂尾的主因，必须明确以下机制。

### 4.1 数据修正与回填 (Backfill & Correction)
* **场景**：昨天逻辑写错（加法变减法），历史数据全脏。
* **流程**：
    1.  用户提交“重算任务”，指定时间段（如昨日 00:00-24:00）。
    2.  系统启动离线任务（Flink Batch/Spark），重读 Kafka/HDFS。
    3.  覆盖 ClickHouse 历史数据（Redis 数据可视情况刷新）。

### 4.2 变更管理与下线保护 (Change Management)
* **场景**：修改被高频调用的指标。
* **流程**：
    1.  **影响评估**：提交修改时，系统弹窗提示“指标X正被风控系统调用，QPS 500”。
    2.  **版本控制**：修改默认生成 v2，不覆盖 v1。
    3.  **下线阻断**：若指标仍有 API 流量，禁止点击“下线”按钮。

### 4.3 新维度热加载 (Hot Reload)
* **场景**：业务方加“App版本”维度。
* **流程**：
    1.  在 MySQL 注册新维度。
    2.  **关键技术点**：Flink 任务**不应重启**。需通过广播流（Broadcast Stream）每 5 分钟同步配置，动态识别新维度并生成 Key。

### 4.4 数据质量 SLA 闭环
* **流程**：
    1.  **T+1 对账**：每日凌晨自动对比 Redis 快照与 ClickHouse 汇总。
    2.  **误差公示**：误差 > 5% 自动触发研发告警，并在界面向用户公示数据质量风险。

## 五、 API 与 SDK 体验升级

### 5.1 API 增强
* **缓存与预热**：支持 `cache_ttl` 参数，应对热点查询。
* **元数据增强**：查询结果不仅返回 Value，可选返回 `metadata`（单位、精度、名称）。

### 5.2 SDK 建设
* 提供 Python/Java SDK，封装重试、批量查询、变更监听（Webhook封装）及规则评估逻辑。

## 六、 实施优先级路线图 (Roadmap)

### Phase 1: MVP 信任构建 (P0 - Immediate)
* **核心目标**：让用户敢用，出了问题能看见。
* **功能**：
    1.  **API Playground (在线调试)**：集成 GMS/GMA 调试。
    2.  **指标“健康灯”**：最基础的死活监控。
    3.  **指标版本管理**：支撑业务迭代刚需。
    4.  **T+1 对账脚本**：发现数据不一致。

### Phase 2: Alpha 场景深化 (P1 - Next Quarter)
* **核心目标**：满足信贷、交易的复杂需求。
* **功能**：
    1.  **在线试算/调试器**：Flink 逻辑验证。
    2.  **指标解释性 & 置信度**：信贷合规。
    3.  **事务性查询参数**：交易一致性。
    4.  **数据修正/重算流程**：解决逻辑错误导致的脏数据。

### Phase 3: Beta 智能化与自动化 (P2 - Future)
* **核心目标**：提升效率，支持推荐等高阶场景。
* **功能**：
    1.  **向量指标支持**。
    2.  **指标全景图与血缘可视化**。
    3.  **维度热加载 (广播流)**。
    4.  **SDK 高级功能**。

---

**总结**：
当前的后端架构是稳健的骨架，但需要通过**调试器、全景图、版本管理、数据修正**等“血肉”功能，将其包装成一个对用户友好、透明且安全的 SaaS 产品。优先解决“黑盒”问题，再逐步深耕垂直场景。
