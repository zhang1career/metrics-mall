## 2. 详细评审

### 2.1 功能需求符合度

#### ❌ 2.1.1 快照写入接口 - 不符合（批量写入缺失）

**PRD要求**:
- 提供新的 HTTP POST 接口，允许业务方上传一组指标及其数值
- **支持批量写入（单次请求可包含多个指标快照）**（PRD 3.1.1明确要求）

**设计文档**:
- ✅ 提供了 `POST /api/v1/m_snap/write` 接口
- ✅ 支持上传指标及其数值
- ❌ **缺失批量写入能力**：当前设计单次请求只能写入一个 `biz_id` 的快照，不支持批量写入多个快照

**建议**:
- **必须补充批量写入接口设计**，支持单次请求写入多个快照（建议最多100个）
- 建议格式：
```json
{
  "project": "credit_loan",
  "snapshots": [
    {
      "biz_id": "txn_001",
      "trace_id": "00-xxx-01",
      "entity_type": "user",
      "entity_id": "u88888",
      "metrics": {...},
      "context": {...}
    },
    {
      "biz_id": "txn_002",
      "trace_id": "00-yyy-01",
      "entity_type": "user",
      "entity_id": "u88888",
      "metrics": {...},
      "context": {...}
    }
  ]
}
```
- 批量写入接口应返回每个快照的写入结果（成功/失败）
- 建议新增接口：`POST /api/v1/m_snap/batch_write`，或扩展现有接口支持批量模式

#### ✅ 2.1.2 数据来源模式 - 符合

**PRD要求**: 支持客户端主导（Client-driven）和服务端主导（Server-driven）两种模式（PRD 3.1.2）

**设计文档**: 
- ✅ 明确支持两种模式：`write_mode` 参数支持 "client"、"server"、"auto"
- ✅ 客户端主导模式：业务方将之前查询到的指标值传回，系统只负责存储
- ✅ 服务端主导模式：未提供的指标由服务端查询实时值
- ✅ 支持 `clientWriteOnly` 字段约束：`clientWriteOnly=1` 的指标只能通过客户端写入
- ⚠️ **类型不一致**：设计文档中 `write_mode` 定义为数字类型（0），但说明中写的是字符串（"client" | "server" | "auto"），需要统一

#### ✅ 2.1.3 业务标识 - 符合

**PRD要求**: 
- 必须强制传入分布式追踪ID（`trace_id`），用于链路追踪和审计溯源（PRD 3.1.3）
- `biz_id` 作为业务唯一流水号，用于关联业务事务

**设计文档**: 
- ✅ `biz_id` 为必填项，符合要求
- ✅ `trace_id` 为必填项，支持OpenTelemetry TraceID格式，符合要求

#### ✅ 2.1.4 上下文记录 - 符合

**PRD要求**: 
- 支持写入非指标类的上下文信息（如 IP、设备指纹、用户ID等）
- 支持用户自定义动态维度（PRD 3.1.4）
- 动态维度实现策略分三个阶段演进：短期JSON+物化列混合，中期Schema版本化，长期智能动态注册

**设计文档**: 
- ✅ 提供了 `context` 字段，支持约定字段和用户自定义动态维度
- ✅ 详细说明了动态维度的使用、存储、查询和管理（第4章）
- ✅ 分阶段演进策略与PRD要求一致

#### ⚠️ 2.1.5 热数据查询 - 部分符合

**PRD要求**:
- 支持通过 `biz_id` 在24小时内以极低延迟查询快照（PRD 4.1）
- 查询接口响应时间目标：P99 < 10ms
- 仅支持点查（按 `biz_id` 精确查询）
- 支持通过 `trace_id` 查询（仅支持冷存储查询，用于链路追踪和审计场景）

**设计文档**:
- ✅ 提供了查询接口 `POST /api/v1/m_snap`
- ✅ 优先查询Redis，响应时间目标P99 < 10ms
- ✅ 支持降级查询ClickHouse
- ✅ 支持通过 `trace_id` 查询（仅支持冷存储）
- ⚠️ **接口路径不一致**：写入接口路径为`/api/v1/m_snap/write`，查询接口路径为`/api/v1/snapshot/query`，路径命名不一致，建议统一
- ✅ **返回格式合理**：返回格式包含完整的快照数据（biz_id、trace_id、timestamp、entity、metrics、context），符合PRD要求

#### ✅ 2.1.6 冷数据归档 - 符合

**PRD要求**: 
- 所有写入的快照数据必须全量归档至分析型数据库（PRD 4.2）
- 支持长期存储和复杂分析
- 支持按时间范围、指标名称、维度等条件进行聚合查询

**设计文档**: 
- ✅ 通过Kafka异步写入ClickHouse，符合要求
- ✅ 支持长期存储和复杂分析
- ✅ 支持按时间范围、指标名称、维度等条件进行聚合查询（通过ClickHouse实现）

### 2.2 非功能需求符合度

#### ✅ 2.2.1 性能要求 - 符合

**PRD要求**:
- 写入延迟P99 < 20ms，P95 < 10ms
- 吞吐量5000+ QPS

**设计文档**: ✅ 目标SLA一致，符合要求

#### ✅ 2.2.2 数据时效性 - 符合

**PRD要求**:
- 热存储保留时间默认24小时，支持自定义TTL（最长7天）（PRD 5.2.1）
- 冷存储保留时间6个月以上（PRD 5.2.2）

**设计文档**:
- ✅ 热存储TTL符合要求（默认24小时，最长7天）
- ✅ 冷存储TTL设置为6个月（`TTL event_time + INTERVAL 6 MONTH`），符合PRD要求（6个月以上）

#### ✅ 2.2.3 可靠性 - 符合

**PRD要求**:
- 热存储写入失败视为接口失败（PRD 5.3.1）
- 冷存储异步写入，不允许数据丢失（PRD 5.3.1）
- 并发写入一致性保障：对于客户端写入快照数据，需要执行"读取快照 → 更新字段（a、ts、h）→ 写入快照"的操作，该操作必须使用Lua脚本实现原子性（PRD 5.3.2）

**设计文档**: 
- ✅ 热存储写入失败视为接口失败，符合要求
- ✅ 冷存储异步写入，提供了容错和重试机制，不允许数据丢失
- ✅ 明确说明使用Lua脚本实现并发写入原子性，符合PRD要求（5.3.1节详细说明）

### 2.3 风险与约束符合度

#### ✅ 2.3.1 容量限制 - 符合

**PRD要求**: 单次请求Payload大小限制为10KB

**设计文档**: ✅ 参数校验中包含大小限制检查

#### ⚠️ 2.3.2 查询限制 - 部分符合

**PRD要求**:
- 热数据仅支持按 `biz_id` 点查（PRD 6.2）
- 热数据查询频率限制：单用户1000 QPS（PRD 6.2）

**设计文档**:
- ✅ 查询逻辑符合点查要求
- ❌ **查询频率限制未明确说明**：设计文档在限流策略中只说明了写入频率限制（单用户100 QPS、单项目1000 QPS、全局5000 QPS），但未说明查询接口的频率限制（PRD要求单用户1000 QPS）

**建议**:
- 在限流策略中明确说明查询接口的频率限制：
  - 单用户（API Key）查询频率限制：1000 QPS
  - 单项目查询频率限制：5000 QPS
  - 全局查询频率限制：10000 QPS
- 建议在API Gateway层实现基于API Key的限流

#### ❌ 2.3.3 数据安全 - 不符合

**PRD要求**:
- 所有写入数据需进行权限校验（API Key认证）（PRD 6.3）
- 敏感数据支持加密存储（可选）（PRD 6.3）
- 支持数据访问审计日志（PRD 6.3）

**设计文档**:
- ❌ **API Key认证未明确说明**：虽然项目中有API Key设计，但设计文档中未明确说明快照写入接口和查询接口的认证机制
- ❌ **加密存储未说明**：未说明敏感数据的加密存储方案（可选功能）
- ❌ **审计日志未说明**：未说明数据访问审计日志的实现

**建议**:
- 在接口设计章节明确说明：
  - 所有接口需要通过 `X-API-Key` Header进行认证
  - API Key需要具备 `write` 权限才能写入快照
  - API Key需要具备 `read` 权限才能查询快照
  - 参考 `SAAS-ARCH-20251214.md` 中的API Key设计
- 说明敏感数据的加密存储方案（可选功能）：
  - 建议使用AES-256加密
  - 加密密钥存储在密钥管理服务（KMS）中
  - 在Redis和ClickHouse中存储加密后的数据
- 说明审计日志的实现方式：
  - 记录操作类型（写入/查询）
  - 记录操作时间
  - 记录操作者（API Key）
  - 记录操作对象（biz_id、trace_id）
  - 记录操作结果（成功/失败）
  - 审计日志存储到独立的审计表或日志系统

- 返回每个快照的写入结果（成功/失败），支持部分成功场景
- 批量写入时，如果某个快照写入失败，不应影响其他快照的写入

#### 3.1.2 统一接口路径命名（P1）


#### 3.1.3 统一write_mode类型定义（P1）

## 6. 评审结论

### 6.1 总体评价

设计文档整体符合需求，架构设计合理，但在以下方面需要补充和完善：
1. **批量写入功能缺失**：PRD明确要求支持批量写入，但设计文档只支持单个快照写入
2. **数据安全细节缺失**：API Key认证、审计日志等PRD明确要求的功能未在设计文档中明确说明
3. **接口设计细节**：接口路径命名不一致、类型定义不一致等细节问题需要统一

### 6.2 建议

**建议继续推进项目**，但需要：
1. **必须补充批量写入接口设计**（P0，PRD明确要求）
2. **必须补充API Key认证说明**（P0，PRD明确要求）
3. 统一接口路径命名和类型定义（P1）
4. 补充查询频率限制说明（P1，PRD明确要求）
5. 补充审计日志说明（P1，PRD明确要求）
6. 补充加密存储说明（P2，可选功能）

### 6.3 风险提示

1. ❌ **批量写入缺失**：可能影响高并发场景下的性能，业务方需要多次调用接口，增加网络开销和延迟
2. ❌ **安全细节缺失**：可能影响生产环境的安全性，缺少API Key认证可能导致未授权访问
3. ⚠️ **接口路径不一致**：可能影响业务方的集成，增加理解成本
4. ⚠️ **查询频率限制未明确**：可能导致系统过载，影响其他业务
