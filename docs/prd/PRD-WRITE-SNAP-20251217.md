# PRD: GMS 快照写入功能

**文档版本**: v1.0  
**创建日期**: 2025-12-17  
**项目名称**: Metrics Mall  
**功能模块**: GMS (接口A) 快照写入能力升级  
**面向对象**: 业务研发（交易/风控/模型）、审计人员  
**优先级**: P0 (高)

---

## 1. 背景与目标

### 1.1 背景

目前 GMS (General Metric Service) 仅提供"只读"的实时状态查询。随着交易链路和模型训练的精细化，业务方需要将决策时刻的指标状态进行"固化"和"留痕"。

### 1.2 目标

本功能旨在提供一个高性能的快照写入接口，满足以下核心需求：

- **事务一致性验证**：记录交易决策时刻的指标状态，用于后续核对
- **特征落盘**：确保离线训练数据与在线推理数据的时间点完全一致
- **审计溯源**：支持监管合规检查，提供不可篡改的历史记录

## 3. 功能需求 (Functional Requirements)

### 3.1 快照写入 (Snapshot Writing)

#### 3.1.1 接口能力

- 提供新的 HTTP POST 接口，允许业务方上传一组指标及其数值
- 支持批量写入（单次请求可包含多个指标快照）

#### 3.1.2 数据来源模式

支持**客户端主导 (Client-driven)** 和**服务端主导 (Server-driven)** 两种模式：

**客户端主导模式 (Client-driven)**：
- 业务方将之前查询到的（或计算好的）指标值传回给接口
- 系统只负责存储，不负责重新查询实时值
- **设计理由**：避免时间窗口导致的数据不一致问题
- **适用场景**：需要即时一致性的场景（如风控决策、交易核对）

**服务端主导模式 (Server-driven)**：
- 业务方可以只传入部分指标值，未提供的指标由服务端查询实时值
- 系统负责查询并存储完整的指标快照
- **适用场景**：可以接受服务端查询的场景（如统计分析、报表生成）

**指标写入约束**：
- 每个指标定义中包含 `clientWriteOnly` 字段：
  - `clientWriteOnly = 0`（默认）：指标既可以通过客户端更新，又可以通过服务端更新
  - `clientWriteOnly = 1`：指标只能够通过客户端更新，不允许服务端查询
- 查询指标信息时，`clientWriteOnly` 字段会出现在指标信息中，用以表明该指标具有即时一致性要求

#### 3.1.3 业务标识

- 必须强制传入分布式追踪ID（`trace_id`），用于链路追踪和审计溯源
- `trace_id`：分布式追踪ID，用于链路追踪（如 OpenTelemetry TraceID 格式）
- 两者可能相同，也可能不同，取决于业务场景
- 支持业务方自定义标识格式（字符串类型）

#### 3.1.4 上下文记录

- 支持写入非指标类的上下文信息（如 IP、设备指纹、用户ID等）
- 上下文信息与指标快照一起存储，用于后续分析
- **实现方式**：
  1. **约定方式**：研发方和业务方通过约定方式定义上下文字段（如 `client_ip`、`device_model`）
  2. **用户自定义动态维度**：用户可以约定或定义每一次请求的上下文信息，支持动态键值对
     - 动态维度与约定字段一起存储在 `context` 字段中
     - 支持通过动态维度进行查询和分析（在冷存储中实现）

**动态维度实现策略（分阶段演进）**：

- **短期（MVP阶段）**：采用 JSON + 物化列混合方案
  - 动态维度无需预先注册，可直接在请求中传入
  - 高频查询的维度通过物化列优化性能
  - 保留 JSON 原始数据，支持任意字段
  - 向后兼容，历史数据可用

- **中期（Beta阶段）**：采用 Schema 版本化方案
  - 支持动态维度注册功能
  - 每次注册后定义完整的 schema，写入时不允许动态修改
  - 如需修改，需要再次更新注册（创建新版本）
  - 支持多版本并存，历史数据无需迁移

- **长期（GA阶段）**：采用动态物化列注册方案
  - 自动化的动态维度注册和管理
  - 系统自动检测新维度并创建物化列
  - 支持智能优化（根据查询频率自动决定是否物化）
  - 完整的版本管理和迁移策略

## 4. 数据查询与存储

### 4.1 热数据查询

- 支持通过 `biz_id` 在短时间内（如 24小时）以极低延迟查询快照
- 查询接口响应时间目标：P99 < 10ms
- 仅支持点查（按 `biz_id` 精确查询），不支持范围查询或模糊搜索
- 支持通过 `trace_id` 查询（仅支持冷存储查询，用于链路追踪和审计场景）

### 4.2 冷数据归档

- 所有写入的快照数据必须全量归档至分析型数据库
- 支持长期存储和复杂分析
- 支持按时间范围、指标名称、维度等条件进行聚合查询

## 5. 非功能需求 (Non-Functional Requirements)

### 5.1 性能要求 (SLA)

#### 5.1.1 写入延迟

- 接口响应时间（RT）P99 < 20ms
- 接口响应时间（RT）P95 < 10ms

#### 5.1.2 吞吐量

- 设计目标需支撑 **5000+ QPS** 的并发写入
- 支持水平扩展，通过增加节点提升吞吐量

### 5.2 数据时效性 (TTL)

#### 5.2.1 热存储 (Redis)

- 保留时间默认为 **24小时**
- 超时后自动过期，释放内存
- 支持配置自定义 TTL（最长不超过 7天）

#### 5.2.2 冷存储 (ClickHouse)

- 保留时间 **6个月** 以上（具体根据存储成本配置）
- 支持数据压缩和归档策略
- 支持按需延长保留时间（企业版功能）

### 5.3 可靠性

#### 5.3.1 异步解耦

- **热存储写入失败**：视为接口失败，返回错误码，业务方可选择重试
- **冷存储写入**：采用异步写入，允许秒级延迟，但不允许数据丢失
- 冷存储写入失败时，需记录失败日志并支持补偿机制

#### 5.3.2 数据一致性

- 热存储和冷存储的数据必须保持一致
- 支持数据校验机制，确保数据完整性
- **并发写入一致性保障**：
  - 对于客户端写入快照数据，需要执行"读取快照 → 更新字段（a、ts、h）→ 写入快照"的操作
  - 该操作必须使用 **Lua 脚本**实现原子性，避免多线程/多客户端并发写入导致的数据不一致问题
  - Lua 脚本在 Redis 中原子执行，确保"读取-修改-写入"操作的原子性
  - 历史记录列表（h）维护逻辑：将旧的 a、ts 值插入列表，只保留预设的列表长度（MAX_HISTORY_DEPTH）

## 6. 风险与约束

### 6.1 容量限制

- **单次请求的 Payload 大小限制为 10KB**，防止大对象阻塞网络或内存
- 超过限制的请求将被拒绝，返回 400 错误码
- 建议业务方将大批量数据拆分为多个请求

### 6.2 查询限制

- **热数据仅支持按 `biz_id` 点查**，不支持范围查询或模糊搜索
- 复杂查询需求需使用冷存储（ClickHouse）接口
- 热数据查询频率限制：单用户 1000 QPS

### 6.3 数据安全

- 所有写入数据需进行权限校验（API Key 认证）
- 敏感数据支持加密存储（可选）
- 支持数据访问审计日志
