# PRD:双速实时指标系统

## 1 产品概述

### 1.1 产品定位

构建一个轻量级、高性价比的实时指标平台,采用"双速"架构设计:

快车道(GMS):毫秒级实时决策查询
慢车道(GMA):亚秒级多维分析查询

### 1.2 目标用户

中小企业广告投放团队
独立游戏/应用开发者
需要实时数据分析但预算有限的技术团队

### 1.3 核心价值

高性价比:单机或小集群即可支撑百万级日数据量
即插即用:标准化SDK接入,最小化开发成本
双重保障:同时满足实时决策和历史分析需求

## 2 系统能力指标

### 2.1 性能指标

指标类型目标值说明数据量级100万行/天起步阶段设计容量GMS延迟<10ms单点值查询(如当前积分)GMS
QPS1000+高频实时查询场景GMA延迟<1s聚合分析查询GMA QPS10+OLAP分析场景

### 2.2 可靠性指标

数据准确性: 99.99%
系统可用性: 99.9%
数据延迟: 端到端<3秒

## 3 技术架构

### 3.1 架构设计原则

采用Lambda架构变体,核心策略为"流批一体、读写分离":
业务系统 → SDK → Kafka → Flink → ┬→ Redis(热存储/GMS)
└→ ClickHouse(冷存储/GMA)

配置管理 ← MySQL(元数据/系统大脑)

### 3.2 组件选型

模块技术选型核心职责选型理由数据源Kafka数据缓冲与解耦业务通过SDK发送JSON日志,高吞吐、可靠传输计算层Flink实时流处理与分流数据清洗、实时计算、双路分发热存储RedisGMS快速响应Key-Value存储最新快照,覆盖写入,延迟<
10ms冷存储ClickHouseGMA历史分析列式存储,高效聚合,支持复杂Group By元数据MySQL配置与血缘管理存储指标定义、维度定义、依赖关系

### 3.3 技术决策说明

不采用的技术及原因:

❌ Hive: 批处理延迟高(分钟级),不满足秒级实时性需求
❌ MySQL存指标数据: 行式存储不适合海量时序数据,仅用作配置库

架构权衡:

✅ Redis覆盖写入: 仅保留最新值,牺牲历史完整性换取极致性能
✅ ClickHouse全量存储: 保留所有历史明细,支持任意维度回溯分析
✅ Flink双路分发: 同一数据流同时写入快慢两路,确保数据一致性

## 4 核心功能模块

### 4.1 数据接入层

#### 4.1.1 SDK规范

功能描述:
提供多语言SDK(Java/Python/Go),标准化JSON格式上报。
JSON Schema示例:

```json
{
  "metric_name": "user_credit_score",
  "timestamp": 1701234567890,
  "dim": {
    "user_id": "12345",
    "region": "us-west",
    "device": "ios"
  },
  "value": 850
}
```

**核心能力:**

- 自动批量提交(默认100条或1秒)
- 本地缓冲与断线重连
- 数据压缩(可选gzip)

#### 4.1.2 Kafka Topic设计

- **Topic命名**: `metrics.raw.{业务线}`
- **分区策略**: 按`user_id`或`metric_name`哈希分区
- **保留策略**: 7天(可配置)

### 4.2 实时计算层

#### 4.2.1 Flink任务职责

**主要处理逻辑:**

1. **数据清洗**
    - 字段校验(必填项检查)
    - 时间戳规范化(统一为毫秒时间戳)
    - 异常值过滤(根据指标元数据定义的阈值)

2. **双路分流**

```
Flink Datastream
├─> Redis Sink: 仅保留(key, latest_value, update_time)
└─> ClickHouse Sink: 完整记录(metric_name, timestamp, dim, value)
```

3. **预聚合(可选)**
    - 滑动窗口聚合(如1分钟窗口的sum/avg)
    - 结果同时写入Redis和ClickHouse

#### 4.2.2 容错机制

- **Checkpoint**: 每60秒一次,存储到分布式文件系统
- **重试策略**: Kafka消费失败自动重试3次,指数退避
- **幂等写入**: ClickHouse使用ReplacingMergeTree去重

### 4.3 存储层

#### 4.3.1 Redis设计(GMS)

**数据结构:**

Key格式: metric:{metric_name}:{dimension_hash}

Value格式:

```json
{
  "value": 850,
  "timestamp": 1701234567890
}
```

TTL: 24小时

优化策略:
使用Redis Cluster保证可用性
热点Key监控与自动扩容
LRU淘汰策略

#### 4.3.2 ClickHouse设计(GMA)

表结构:

查询优化:
按月分区,查询自动裁剪
物化视图预聚合常用维度组合
索引优化(Bloom Filter索引用于dims)

### 4.4 元数据管理

#### 4.4.1 MySQL表设计
核心表:
指标定义表 (metric)
维度定义表 (dimension)
血缘关系表 (metric_lineage)

#### 4.4.2 血缘管理的战略价值
**当前阶段:**
- 手动维护血缘关系
- 提供API查询指标依赖链
- 影响分析(某指标变更影响下游哪些指标)

**未来扩展(预留接口):**
- 基于血缘图的智能推荐
- 异常指标自动溯源
- 谓词逻辑推理引擎集成

### 4.5 查询接口
#### 4.5.1 GMS: 实时快照查询

**实现路径**
Redis查询 → 若未命中则查ClickHouse最新记录 → 回种Redis

**性能要求**
- 99%请求命中Redis(<10ms)
- Cache-Aside模式自动预热
- 限流保护(单用户1000 QPS)

#### 4.5.2 GMA: 历史聚合查询

**实现路径**
直接查询ClickHouse → 根据元数据校验查询合法性 → 执行SQL聚合

**查询优化**
自动生成最优SQL(利用分区裁剪)
结果缓存(5分钟TTL)
异步查询支持(超时返回task_id轮询)

## 5 商业落地场景

### 5.1 首选场景:广告投放效果聚合看板
目标客户:
中小型广告投放团队、代理商

核心痛点:
数据分散在Google Ads、Facebook Ads、TikTok Ads等多平台
需要人工整合Excel表格分析ROI
无法实时监控异常消耗并及时止损

解决方案:
数据接入
通过各平台API定时拉取数据(每5分钟)
标准化为统一指标格式(曝光、点击、转化、花费)

实时看板(GMS)
展示当前小时的实时花费
异常检测(如CPC突然上涨20%)并推送告警

趋势分析(GMA)
过去7天/30天的ROI趋势
按地域、设备、广告创意分组对比

商业价值:
节省人工整合时间80%
提前发现异常节省广告预算15-30%
SaaS订阅模式:按广告账户数量收费(¥299/月起)

### 5.2 备选场景:轻量级游戏/应用埋点分析
目标客户:
独立开发者、小型工作室

需要快速验证功能受欢迎程度

解决方案:

即开即用的预置看板
DAU/MAU、留存率、付费率
关键事件漏斗分析(注册→首充→7日留存)

性价比定价
免费额度:10万事件/月
付费套餐:¥99/月(100万事件)

竞争优势:
比自建便宜70%
比大厂产品简单,5分钟上手
专注核心指标,不做复杂归因

## 7 风险与应对

### 7.1 技术风险
| 风险项           | 影响     | 概率 | 应对措施                                    |
|---------------|--------|----|-----------------------------------------|
